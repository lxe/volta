Recommendation: recover the archived vlut2 source for review, but do not build or schedule a candidate until a current primary-DP critical-path budget supports it. The exact source was found in the local box archive after the initial checkout-only search. Its lab models the sliced expert dimensions, but uses generated data and does not establish the present four-agent gain; historical engine integration already lost performance. `VOLTA_SHARED_EARLY=1` has exactly zero effect on the primary DP path. ## vlut2 implementation and compatibility

README.md:316 and DESIGN.md:532 mention Scout's four-warp vlut2 gate/up improvement31.2→18.6us at one token, but DESIGN also says it lost in the engine while the shared slice ran beside it. Those are historical narrative claims, not receipts from this rental. An exact-name search of the active repository finds vlut2 only in those two documentation passages; `git log --all -S vlut2 -- engine/src/kernels tests` finds no implementation-bearing history in the available checkout. There is no registered vlut2 symbol or runtime flag. Current `engine/src/kernels/volta.cuh:930-936` uses `WARPS=8`, and `engine/src/volta.rs:2561-2569` selects existing `vlut_{cb3,cb2,fp4}r1_n1/n2` or n4 kernels.

The complete GGUF reconstructs the existing native code/scales, including its original eight-way expert slices and multipliers (`core/src/volta_quant.rs:103-169,314,605-658`). Native format is words[row_group][unit][word][lane] with byte scales and per-matrix multiplier (`engine/src/kernels/volta.cuh:906-925`). CB3 stores the final pair across the high bits of three words. Any candidate must decode this exact layout and preserve CB3/CB2 scale/multiplier semantics, token-pair maps, dynamic hot lists, split-K atomic accumulation, gate/up row order, down-column slicing, rotations and eight-GPU partial sums.

The actual manifest is format4/ngpu8/etp8, with dim5120 and intermediate2304. Each GPU therefore computes a routed gate/up matrix576×5120 and down5120×288. A claim about a full4608×5120 gate/up does not establish performance for these slices. A code-only decoder/scheduling change could be compatible; the recovered CB3 A1 source described below preserves the native format and has a plausible compatible interface. Its performance and whole-engine numerical behavior still need confirmation. Requantizing weights, changing codebooks or moving to another expert ownership/TP plan would violate the frozen-model scope. A lossless internal reorder would still need its own byte-exact reconstruction, memory/startup budget and numerical proof; it is not justified by the old name alone and must not require publishing a replacement GGUF for this test.

### Recovered kernel resource budget

For CB3, one four-unit staging area is4×3×128+4×32=1664bytes/warp. Four warps add6656bytes/block beyond the original x/table allocation. At KC1024 the candidate dynamic shared-memory request is23,936bytes for NT1 and40,448bytes for NT2; the current eight-warp kernel requests17,280 and33,792bytes respectively. Candidate launches128threads with `__launch_bounds__(128,4)`, which constrains registers for at least four blocks by the compiler's register budget; actual registers/spills and achieved occupancy must be checked in the real build. Shared-memory capacity alone permits at most four NT1 or two NT2 blocks on a96KiB SM. Additional static shared memory or register allocation can lower that. No new persistent model arena or quant layout is needed by this code.

With six hot experts, the gate/up slice has18 row groups. Existing eight-warp blocks give3×6×5=90 useful blocks; four-warp blocks give5×6×5=150. The current grid-y budget also depends on rtiles and kz (`vmoe_lists`), so a future integration must change block size, rtiles and shared-memory size together rather than replacing only a symbol. Retain the existing LUT_BLOCKS policy and explicitly account for its resulting grid; no blind grid sweep.

Six CB3 gate/up slices contain7,188,480bytes including scales, an8.28us streaming floor at the archive's stated868GB/s. The historical18.6us result is about2.25times that conditional floor; decode/prologue costs remain. Repeating the historical12.6us saving over40layers would save0.504ms, about1.47% of the currently observed approximately34.35ms DP decode pass, **only if the six-hot-expert one-token workload applied**. It does not give a bound for a four-session route union. A5% primary target requires about1.72ms net/pass, or43us/layer if spread uniformly, after overlap losses. Current real hot-list counts and main/side-stream critical time are therefore essential before a build can be justified.

## Required resource budget and confirming evidence

For the real TP8 routed slice, CB3 gate/up reads1,198,080bytes and down599,040bytes per distinct expert; CB2 reads829,440 and414,720bytes respectively, including one scale byte per32 weights. Those are1,797,120 or1,244,160bytes total per distinct expert per GPU, before input/output/list traffic and cache reuse. Use measured distinct-expert/bucket counts to compute the layer's actual bytes. Do not multiply by the number of picked tokens when weights are reused, or assume48 distinct matrices from the generated test.

NVIDIA specifies900GB/s V100 HBM bandwidth; a single CB3 gate/up slice would take1.3312us at that optimistic streaming rate, CB2 0.9216us. These are conditional cold-HBM byte floors, not measured kernel latency or universal warm-cache lower bounds. Arithmetic decode, scales, half2 transforms, shared memory, split-K atomics and launch/collective waits add costs. The historical690GB/s figure in DESIGN.md:533 belongs to earlier dense measurements and has not been calibrated for this rental's expert path. [NVIDIA V100 specification](https://www.nvidia.com/en-gb/data-center/tesla-v100/).

Before any implementation: finish reviewing and bind the recovered exact source; identify its intended shapes/layout; retain a source/SASS/register/shared-memory comparison against the active kernels; and obtain existing real routing/bucket and critical-path evidence. If those observations are absent, explicitly budget a minimal parent-owned confirming measurement before writing the larger candidate. Counters require an authorized counter-capable environment; these containers do not supply them. Do not infer a mechanism from source instruction counts alone.

If source and mechanism survive that review, a parent-approved short same-box A/B must use actual GGUF slices, realistic distinct experts and routing, exact baseline launches, ordered and swapped comparisons, and the real per-element math. It must cover gate/up576×5120 and down5120×288 for both codebooks, real small/big expert-count buckets, and overlap with the actual shared slice. Preserve teacher/layer correctness and resource reserve. Kill if correctness fails, if the formerly observed overlap loss recurs, if key shape gains vanish under distinct real weights, or if the measured critical-path budget cannot support at least5% primary improvement. A microbenchmark gain alone does not justify integration or a throughput claim. No positive gain is booked.

## SHARED_EARLY scope and byte floor

`engine/src/volta.rs:3291` sets shared_early only when side_mix, HP, local T<=8, an actual shared slice, and the flag are all true. `route_hp` at2301-2311 explicitly excludes shared_early, so enabling it also replaces the fused HP routing path with the longer general path. It is not a free stream-placement toggle and cannot optimize DP without a separate code change and budget.

The shared expert is split across eight GPUs: sl2304/8=288 (`engine/src/volta.rs:1328-1346`). Each GPU has gate/up576×5120 and down5120×288. Its dense vmoe representation has four code bits and a16-weight fp16 scale, or0.625bytes/weight (`pack` at247-264; `upload_v4_f32` at904-924). Thus gate/up is1,843,200bytes and down921,600bytes, totaling2,764,800bytes/GPU/layer, rather than eight times that amount. A single cold read takes at least about3.072us at900GB/s, or4.007us at the historical690GB/s figure, before launches, input/output and SiLU. These conditional floors do not upper-bound removable critical time: overlap, cache reuse and actual kernel duration must be measured. A floor alone cannot justify a gain ceiling.

For primary DP, the existing flag's gain ceiling is exactly0%, because the HP condition is false. For HP, the source comment's historical6us/layer improvement would amount to0.24ms over40 layers if it repeated uniformly, but it is not a current receipt and the flag additionally disables fused routing. Bound any future HP trial by a paired measured router/shared/expert critical-path delta, not by that old comment. With the current HP sampler validation already scheduled, a blind SHARED_EARLY flag sweep is not warranted.
