# Last-row vocabulary projection feasibility

The current server needs only the final prompt row's distribution while prefilling, but finish() projects every token row through the vocabulary head. A narrow DPslots1 GPU-sampling optimization is feasible without a gather kernel: project the single normalized final row, then use sampler row0. It must preserve all transformer-layer work, token positions and DSpark observations. This is a source-only proposal; no implementation, build or GPU experiment was performed.

## Existing interfaces and a minimal first scope

finish() in engine/src/volta.rs:2668 first computes vhc_pre and output RMS normalization for all t rows, advances every session token position, then runs mm(head,x,logits,t). GPU sample tables already identify each required distribution by rb and nd. The worker has the original CPU table before uploading it in Cmd::StepSample; the server sets prefill rb=r0+n-1,nd0 and decode rb=r0,nd=n-1. No new vocabulary or weight format is required.

For the primary DPslots1 serving configuration, each GPU has at most one active session. A candidate can recognize one StepSample table entry, nd0, rb=t-1, t>=32, ordinary unsplit Lin::V head, and non-HP mode. In that case keep normalized x in place, call the existing head projection with input pointer x+rb*5120*4, t_head1 and output logits row0, and change only that uploaded table's rb to0. The per-GPU rows expected back by step_sample stay one result pair; no external result-shape contract changes. Record/clear the selected-head state for that command only, including error exits, so no later decode inherits it.

Keep the existing full-row vhc_pre/RMS preprocessing initially; this makes the first implementation a head-row selection change, with no extra GPU buffer or gather launch. Advance positions for all original tokens, retain the original plan and t for transformer layers/graph key, and leave DSpark target hidden-state capture and accepted-token observations unchanged. The output head is outside the existing main CUDA graph, so this does not require another graph shape or alter admission.

Multi-slot compaction is a larger follow-up. Existing vgather_rows (kernels/volta.cuh:1557, already registered and used by DSpark) copies float rows by an index table. A compact head would need the union of every decode verification row rb..rb+nd and each prefill final row, plus remapped sampler rb values. It must preserve each entry's consecutive speculative rows; discarding all but the final row of a decode group is incorrect. Existing vmm supports arbitrary contiguous input base/stride but its public wrapper does not accept an arbitrary token-row list. Do not alter those wrappers or reuse live layer scratch speculatively in the first candidate.

## Fallback and quality constraints

Generic Engine::step returns t*vocab logits and is used for teacher evaluation and other callers. Engine::step_greedy returns one argmax per input row; the server's CPU/greedy fallback indexes these arrays by original r0+j. Neither API may silently return compact output. Leave CPU top-p/hesitation fallback, all-greedy StepGreedy, multi-slot requests, HP and generic CLI/eval paths unchanged in the narrow first candidate. A later selected-row API would need explicit row-index/result metadata for every caller, including HP vocabulary-slice reconstruction.

HP's sampled finish downloads each GPU's vocabulary slice to the CPU; it does not use the DP GPU sampler. Last-row selection could eventually help HP too, but its logical multi-session row map and CPU result indexing make it a separate interface change. The current HP throughput loss is not evidence that this one finish operation causes that loss.

The head switches from n4 at32/64rows to n1_r1 at1row. Quantized weight/scales, output normalization and activation rounding stay the same, but different MMA tiles and split-K scheduling need not yield bit-identical logits. Main K5120 is split in five1024-value chunks. Do not promise identical sampled strings. Existing chunk1 teacher quality exercises the small-row head arithmetic but does not exercise the proposed rb remapping or prefill command dispatch, so rerunning that teacher alone cannot prove this change correct.

Before promotion, a diagnostic on real model inputs must compare each original final-row head output against the selected-row projection, checking finite logits, max/relative error, probability KL/top1 and sampling behavior under actual temperatures. Exercise rb31/63, actual short tail rows, mixed prefill/decode GPUs, retries/errors, and confirm every unchanged fallback still returns its original t-row shape. Then require the existing teacher bounds, coherent actual tools and matched four-agent measurements. A synthetic row-address test is useful but is not sufficient real-model numerical evidence.

## Per-step resource budget

Actual head dimensions are vocabulary129280 by model dimension5120. One projection row requires1.3238272GFLOPs (multiply/add count),32rows42.3624704GFLOPs, and64rows84.7249408GFLOPs. Selecting one row removes41.0386432GFLOPs at32 or83.4011136GFLOPs at64. These are arithmetic counts; they are not a64x latency prediction.

The existing head stores330.9568MB packed4bit codes plus82.7392MB f16 scales (one scale per16weights):413.696MB/GPU remains resident. A32-token n4 tile can read the weights once;64tokens traverse two32-row tiles and can reread them. A1-row projection still streams this full413.696MB. At the historical690GB/s small-stream calibration, ideal single/two-read references are0.600/1.199ms. This is a historical hardware reference, not a measured head bandwidth or floor on this rental. Launch, dequant, MMA, split-K accumulation and activation prep costs remain.

FP32 logits shrink from33.09568MB at64rows or16.54784MB at32 to0.51712MB for one row. This removes output zero/write and associated projection work. On the already optimized GPU-sampling server, host transfer is already only8bytes/session; do not count the old33MB D2H removal a second time. No weight upload, quant/tier change, additional pinned RAM, network or disk transfer is needed. The narrow design adds a few CPU metadata integers and a small copied sampling table; it needs zero new persistent GPU allocation and no new kernel. It leaves full64-row fixed workspaces allocated, so it does not free their VRAM reservation.

## Decisive measurement before implementation

The current v2 graph trace measures host enqueue/backpressure around layers and graph decisions; it ends before finish. It cannot attribute head cost. The standalone D2H receipt established the transfer removed by the sampler guard, and the current attention microbench excluded the vocabulary head. Guard A/B speedups therefore supply no measured last-row-head saving. No recorded DP head-specific profile currently justifies an end-to-end gain claim.

One later bounded VOLTA_STEPT run on the DP sampler binary is an appropriate first screen. It synchronizes after layers, then measures finish until its download completes; finish includes HC pre/RMS, vocabulary projection, GPU sampling and the8-byte result download. This is a synchronized finish wall boundary, not isolated head time. Preserve the currently scheduled diag-v2-001/guard-02 protocol; run this profile separately after parent approval, at most one fixed and one mixed controlled four-client trace, with no competing GPU work and no new weights.

If the sum of finish time on the critical path of affected prefill steps is under5% of matched trace wall time, even eliminating finish entirely cannot meet the5% primary gate: stop this candidate. Sum critical per-step maxima over active GPUs, not all eight GPU finish times, and do not count concurrent GPU times as serial savings. A same-budget graph policy win may also change the denominator and must be measured separately.

If finish supplies enough budget, obtain head-specific timing before implementing selection. A short CUDA-event diagnostic around the existing full head and selected-row head on the same normalized input is decisive: it must preserve/copy the original selected logits before overwriting them, report both projection times and the numerical comparison, and keep normalization/sampling separate. A trace that resolves the final head launch sequence after the40th layer can also attribute it if available. Host enqueue timing alone is insufficient because CUDA launches are asynchronous and can backpressure at unrelated boundaries.

Do not run two whole-model layer passes merely to compare the two heads. Reuse a frozen normalized final-row input once, perform both head paths in a diagnostic, and exit; budget one0.517MB reference-row buffer plus at most1.034MB host comparison data, with fixed workspaces retained. The exact CUDA-event source would be a separate diagnostic implementation requiring another approved build/run window. It is not part of the currently compiled graph diagnostic.

Conditional prediction only after that measurement: saved_ms_per_affected_step times the number of affected critical-path steps, divided by matched trace wall time, must predict at least5% primary improvement after added selection cost. Book zero gain before this calculation. Kill on nonfinite output, teacher/probability deviation outside agreed gates, any unchanged fallback regression, no measured head reduction, or under3% initial whole-trace gain. Promote only with swapped-order paired confirmation of at least5% four-agent throughput/makespan improvement, actual equal token/cache work and no more than5% worse p95 inter-token latency. Keep row selection separate from graph admission, kernel rewrites and context changes.

The prepared CPU parser is parse-volta-stept.py with stept-parser-protocol.md. Existing STEPT lines omit t, so a standalone log supplies only per-GPU unknown-t finish bounds. A later combined v2+STEPT run can join positive-t trace records and profile lines from the same process; idle t0 is omitted by STEPT. Separate runs must not be joined. This addition does not change the currently planned diag-v2-001 protocol or launch any workload.

For the real-row comparison, keep the baseline64 projection's final-row logits intact, then project the normalized final-row input into output row0 with t1 and compare the two distributions before sampling. Since rb>=31 in this narrow scope, row0 and the original final row are distinct. Current vprep zeroes only the requested output rows, so the old final row can remain in its existing logits allocation while row0 is replaced; prove that bound in the diagnostic rather than assuming scratch safety. A conservative0.517MB reference copy remains available if needed. Repeating a generic chunk1 teacher check alone still cannot validate the new prefill dispatch/remapping.

## Actual finish gate: candidate rejected

The parent later ran a separate combined v2+VOLTA_STEPT DPslots1 profile, diag-v2-stept-001. Its own server UTC log selects fixed sequences100..393 and mixed394..768. The complete eligible finish upper bounds are247.15ms over16.2360s fixed (1.52%) and702.48ms over27.2165s mixed (2.58%). Typical64-row finish is3.53-3.75ms; it includes normalization, head, sampler and download. Eliminating that whole finish cost would still miss the5% primary gate, so the proposed narrow last-row-head optimization is rejected before implementation.

Eligible coverage is complete: the fixed interval has4145prefill tokens in65chunks on each active GPU; mixed has4145/65 onGPUs0-2 and8242/129 onGPU3, matching every uncached API prompt. The last eligible mixed prefill is sequence608, before the768-step completed snapshot. Missing the final~1.33s of the mixed decoder tail therefore does not omit any work eligible for this t>=32 prefill candidate. Receipts are diag-v2-stept-001-fixed-analysis.json, mixed-analysis.json and head-gate.json. Profile synchronization still makes these diagnostic upper bounds, not primary throughput results. No head implementation/build/GPU comparison was performed by this investigation.
