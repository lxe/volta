# Four-slot step graph admission proposal

A four-slot graph replacement policy is worth considering only after instrumentation shows that repeatedly used step keys run eagerly because the current first-arrival cache is full. The current baseline has393MiB free after the gauntlet and as little as273MiB after4K/8K screens. Increasing the number of resident graphs is outside the previously agreed headroom budget. This proposal preserves four main executable graphs per GPU and leaves the separate draft graph policy unchanged.

## Required evidence before implementation

Add an opt-in CPU-only accounting mode around the existing run_step decision. For each GPU and(t,bucket), count observations, graph launches, eager executions by reason (first encounter, main limit, graph_full, explicit profiling/disabled), capture attempts/success/failure, and elapsed host time spent capturing/instantiating. Record the four resident keys and capture order. Keep counters in a bounded key array/map: t0..64 and at most powers64..262144 give13buckets,845entries per GPU; a few64-bit fields per entry remain well under128KiB/GPU of host memory. Use a summary after each256steps or a controlled end-of-screen snapshot, rather than stderr on every kernel or step. The environment flag defaults off; no extra device synchronization or mem_info call belongs in the per-step counting path.

A key's t<=6 does not by itself prove it is a decode key, because a short final prompt chunk can have that size. Identify sustained small-t misses within the known generated-token phase of the matched trace, using server admission/first-token timestamps and per-key repetition. If necessary record a small per-step CPU decision trace during one diagnostic run (GPU,key,decision,step sequence), bounded to4096records/GPU and emitted after the screen. It must not silently become an unbounded log or part of primary performance timing.

The evidence gate is at least20repeated eager executions of a key in a generated-token phase, and at least25% of main-step calls missing because of admission while a cached key receives no replay during that same phase. Also inspect whether more than four keys are simultaneously hot. A four-slot policy cannot cache six equally frequent shapes; claiming to solve that by replacement would ignore capture churn. If misses are rare, forced by graph_full, or caused mostly by six similarly hot shapes, stop this policy candidate and retain the current source.

An instrument-only binary should reproduce teacher/serving checks and stay within2% throughput of the same uninstrumented binary with accounting off. Run the decision trace as a short diagnostic; do not mix its results with the current guard A/B or alter the frozen gauntlet. No instrumentation or policy implementation has been made for this review.

## CUDA executable destruction

The installed NVIDIA CUDA12.9 header is authoritative local API documentation: /home/lxe/volta-publish-20261024/cuda12/root/usr/local/cuda-12.9/targets/x86_64-linux/include/cuda.h:21628-21670 documents cuGraphExecDestroy and cuGraphDestroy. Executable destruction releases its executable nodes; an in-flight execution is allowed to finish and its resources are freed asynchronously afterward. Destruction therefore does not cancel work, and a successful destroy call alone does not prove its device allocations have already been reclaimed. The header marks these operations with the graph thread-safety note; this engine's per-GPU worker must remain the sole owner/operator of its graph handles.

Current gpu.rs GraphExec wraps only CUgraphExec and has no destructor. Simply removing a map entry would leak the executable rather than free its memory. gpu.rs::end_capture also returns immediately if instantiation fails, skipping destruction of the temporary CUgraph. A replacement implementation must explicitly fix ownership at this boundary: one checked Gpu method consumes a GraphExec under the owning current context, calls cuGraphExecDestroy once, and never leaves an alias that can be launched. Avoid an implicit Drop implementation that silently calls CUDA with an arbitrary context or hides an error during a live serving step. Cleanup on normal shutdown may use a carefully context-bound owner, but that is separate from checked eviction.

To preserve the resident-memory budget, evict only at a worker step boundary outside capture. Flush pending mega operations (although this run keeps mega off), synchronize both the owning main and side streams, then destroy the selected executable under that GPU's context and check the return status. Synchronizing both streams makes prior execution completion explicit, including an idle t0 GPU whose run_step returned without finish/download. Do not call a global cross-GPU barrier or synchronize midway through a captured collective; all peers' prior steps must already have been launched. Never free weights, scratch, KV, tables or peer buffers referenced by any retained graph.

Only after destruction may the replacement graph be instantiated. This permits no fifth retained executable, but the temporary capture graph and driver instantiate workspace may still require transient memory. Check measured headroom before admission and measure peak usage; the four-handle count is not a byte-exact allocation guarantee. On every end_capture outcome, destroy a non-null temporary CUgraph after the instantiate attempt, preserving the original instantiate error if both fail. If capture or destruction fails, disable further policy admissions for this process, preserve raw errors and restart through the owned server controller before further performance comparisons. Do not repeatedly chase memory exhaustion with retries.

## Minimal policy if the evidence gate passes

Keep the(t,bucket) key, all layer computation, GPU tables and draft cache unchanged. Replace Option<GraphExec> main entries with explicit warm-up/captured state and CPU recency/frequency metadata. Enforce the four-executable limit at every capture attempt, including previously warmed keys; graph_full must block every new capture while permitting existing replays. This removes the current absent-key-only cap bypass without changing numerical work.

Pure second-touch LRU is small but can repeatedly capture when adaptive draft counts vary among more than four hot keys. Prefer bounded frequency admission with hysteresis: maintain counts in a sliding64-step key window; require an uncached key to appear at least8times in that window and to exceed the least-frequent resident key by at least4observations. Break victim ties by oldest last replay. When fewer than four slots exist, retain the existing second-occurrence warm-up rule; once full, use the stronger replacement threshold. First use still runs eager so cuBLAS/kernel attributes and per-shape tables are warm before capture. Do not prioritize token count alone; frequency lets a genuinely reused prefill key compete on its measured use.

Allow at most one replacement per64main steps per GPU and at most eight replacements/GPU for the entire bounded trial. After that stop admissions while replaying retained graphs. This bounds capture work to64replacement instantiations across the box, prevents a two-key oscillation, and makes a failed policy visible instead of consuming the remaining rental. These constants are a proposed first screen, not an optimized production policy. CPU-only simulation should first replay the actual recorded key trace to show improved hit coverage under the four-slot budget and report capture count; a synthetic trace alone is insufficient evidence.

Frequency hysteresis delays replacement of a very frequent early prefill key until its observations age out. That is deliberate: a one-off decode key should not evict a repeatedly used prefill graph. The first64generated steps may remain eager. If this delay or repeated context-bucket changes erase the expected benefit on the actual agent trace, reject the policy rather than shortening thresholds without another budgeted hypothesis.

## Resource budget, prediction and kill criteria

Resources: at most four retained main executables per GPU, unchanged draft executables and all tensor allocations; under128KiB/GPU extra host counters, a64-entry key ring, and optional bounded diagnostic records. No bulk I/O, network or weight conversion. Replacement adds a main/side completion wait and one capture/instantiate at most every64steps/GPU. Reclaim a victim before instantiating its replacement. Historical graph budgets do not supply bytes/executable, so preserve actual device-memory measurements rather than inventing a per-graph estimate.

The initial memory gate requires at least the matched four-slot baseline's measured free-memory low watermark minus32MiB, and never below192MiB/GPU. This is a proposal for a same-budget trial, deliberately distinct from the rejected1GiB gate for increasing graph count. If the parent prefers retaining the existing stronger headroom requirement, the candidate remains blocked; this proposal does not authorize weakening it. A free-memory check cannot guarantee the driver's transient instantiate request fits. Stop on any capture/instantiate error, more than32MiB/GPU lower free memory than the matched baseline, or loss of the192MiB reserve. Sample memory between requests/at1second cadence and retain raw allocation errors; no pinning, register, precision, tier or global configuration changes.

Prediction, conditional on the evidence gate and successful trace simulation: replacing stale graphs with repeatedly missed decode keys improves generated-token phase throughput by5-12%, with a smaller or zero whole-trace gain after capture waits. Book zero gain until matched measurement. The evidence must connect actual missed keys to new hits; a speed difference without this mechanism check is insufficient attribution.

Bound implementation and simulation to45minutes; first actual screen at most10minutes plus model reload, on a single chosen binary/config after the guard experiment. Hold chunk64,DPslots1,context131072,spec5,sampling and exact warm-up/prompt nonces fixed. Require teacher regression gates, matching API success/tool behavior, actual output-token accounting, and no more than5% p95 inter-token regression. Kill if CPU trace simulation predicts under15percentage-point graph-hit coverage improvement, more than eight needed replacements/GPU, observed generated throughput improves under3%, whole matched trace makespan regresses over2%, or any resource/correctness gate fails. Promote only after swapped-order paired confirmation shows at least5% median primary four-agent throughput/makespan improvement with the predicted hot-miss reduction. Do not combine this with graph16, chunk changes, last-row head work or dense kernels.
