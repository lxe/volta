# Head-parallel GPU sampling feasibility

The actual V3 HP4/256K profile passes the CPU-cost gate: fixed CPU distribution/RNG work is8.90630s of40.858084s SSE wall (21.7981%); mixed is10.23597s of48.132269s (21.2663%). These sums time the Rayon join once, not each worker. Both phases produced2048 tokens with zero cache reuse. Instrumentation perturbs runtime; the fractions identify a candidate and do not establish an optimized speed.

## Existing interfaces and proposed data path

HP spreads the caller's single plan to all8GPUs. Each head currently writes a packed[t][16160] FP32 vocabulary slice, downloads it, and Engine::step allocates[t][129280] and copies slices into vocabulary order on CPU. Work::logits already reserves64x129280 floats perGPU, although the HP projection writes a packed slice. The server disables GPU sampling whenever head_parallel() is true, and Engine::step_sample explicitly rejects HP. Removing these guards alone would sample incomplete logits and is invalid.

A separate HP sampled-step mode can preserve every head/math kernel and collect the8 packed slices into one new GPU0 full-vocabulary buffer, then launch the existing vspec_sample. Exchange each worker's logits pointer and primary-context handle alongside PeerBufs. Gpu.ctx is currently private to gpu.rs; expose a narrow method/helper rather than changing context ownership. Send the same sampling tables to GPU0 and explicitly mark all workers as participating in the HP sampled command, including workers with zero table rows. Engine must spread the single HP plan and return only GPU0's result. DP, greedy, top-p<1, hesitation, disabled GPU-sampling, unsplit/unsupported head, and generic CPU step paths retain their present behavior. Validate total plan rows<=64, table rows<=64, local vocabulary divisibility and actual split_head before admission; retain nd<=8 per generated entry and arbitrary prefill last-row index.

After local head projection, each worker calls its own g.sync(), then a host barrier establishes that all8source slices are ready. GPU0 queues7 cross-context pitched copies plus one local pitched copy on its own stream, followed by vspec_sample and the existing result download. Other workers return an empty result. Engine already waits for all8results before returning to its sole synchronous server caller; this prevents next-step commands from overwriting source buffers before GPU0 completes. Avoid adding another unmatched barrier after early worker returns; any pre-barrier error must use the existing immediate-fatal worker-error contract, otherwise a waiting thread could deadlock.

## CUDA copy contract

NVIDIA documents cuMemcpy3DPeerAsync as asynchronous cross-context copying on a supplied stream, with explicit source/destination contexts. CUDA_MEMCPY3D_PEER provides byte pitches, byte width, height and depth; it permits zero slice-height when depth is1. Use DEVICE operands, WidthInBytes64640, Height=t, Depth1, source pitch64640, destination pitch517120 and destination X offset64640*g. Set unused offsets/LOD/pointers to zero and check pitch limits. GPU0 remains current and supplies its non-default stream. Source g.sync plus the host barrier establishes readiness; stream ordering puts sampling after copies, and result-download synchronization establishes completion. Use cuMemcpy3DAsync for GPU0's local nonoverlapping copy rather than relying on undocumented same-context behavior of the peer function. These API contracts are documented in [CUDA12.9.1 memory management](https://docs.nvidia.com/cuda/archive/12.9.1/cuda-driver-api/group__CUDA__MEM.html) and [peer-copy fields](https://docs.nvidia.com/cuda/archive/12.9.1/cuda-driver-api/structCUDA__MEMCPY3D__PEER__v1.html). They establish correctness semantics, not guaranteed overlap or NVLink bandwidth.

## Resource and experiment budget

One separate64-row full-vocabulary buffer costs33,095,680bytes=31.56MiB on GPU0. Reusing its existing packed-slice allocation in place would overlap reads and writes, so do not do that. Existing sampling tables/results suffice; host/context-address metadata is below1KiB. At t64 the7 remote slices total28,958,720bytes, plus4,136,960local bytes. At four generated sequences with up to6rows each, t<=24 and remote payload<=10,859,520bytes. This removes the existing33.1MB maximum aggregate D2H and CPU merge/distribution, but retains all head arithmetic, FP32 logits and GPU sampling scans. No quantization change, new kernel/fatbin, dense-row gathering or graph-policy change belongs in this candidate.

The copied HP profile memory receipt must verify the192MiB reserve after31.56MiB additional allocation, and actual candidate guard must pass its first observation before requests. The historical DP memory state does not establish HP capacity. Compile and GPU budgets require separate parent authorization. A potential bounded screen is one small teacher gate, then actual HP sampled-row comparisons and matched fixed/mixed runs; no current authorization to implement/build/launch is inferred.

The zero-new-cost ceiling is approximately27–28% higher HP TPS from the observed CPU share. A screening prediction is10–20% higher HP TPS after peer-copy/sampling overhead; no gain is booked. Even that would not establish HP as the primary four-agent throughput winner over DP. Kill on any collected-logit byte mismatch, output/token/RNG-consumption mismatch versus existing sampling semantics, deadlock, reserve breach, unchanged-kernel hash mismatch, teacher-gate failure or less than5% matched HP fixed/mixed gain. CPU and GPU samplers use different reduction precision, so identical stochastic token sequences are not a universal quality invariant; bind exact uniforms to gathered logits and compare existing GPU sampler behavior, while using real teacher/distribution gates for model quality.

Before performance claims, decisive correctness evidence must compare every collected FP32 logit bit against the current CPU HP concatenation for real multi-slot prefill/decode rows, including rb63, mixed greedy/temperature, speculative acceptance/rejection and tails. Existing teacher chunk1 alone will not exercise StepSample. Reuse the frozen vspec_sample for uniform-boundary and draw-count tests; preserve CPU fallback. Paired same-configuration timing and continuous memory receipts are required after those checks. This document authorizes no experiment.
